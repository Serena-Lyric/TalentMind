# 04 前端控制界面联调需求

## 目标

让前端能够设计一个“采集控制台”，至少能回答：当前是否运行、采集到了哪一组、这一轮做了多少、数据库累计多少、为什么停止、下一步需要用户做什么。

前端可自行决定布局和交互，不要求采用本文的页面结构。本文只列出可供设计的语义。

## 建议控制动作

| 动作 | 语义 | 当前后端状态 |
|---|---|---|
| `start_once` | 启动一轮连通性/增量采集 | CLI 已支持，控制 API 未实现 |
| `start_continuous` | 按低速节奏不间断轮换 | CLI 已支持，控制 API 未实现 |
| `start_limited` | 启动指定轮数 | CLI 已支持 `--rounds`，控制 API 未实现 |
| `pause` | 暂停在安全边界 | 当前未实现，需后端设计 |
| `resume` | 从暂停状态继续 | 当前未实现，需后端设计 |
| `stop` | 主动停止当前任务 | 当前可通过进程控制实现，API 未实现 |
| `refresh_status` | 拉取任务/CDP/数据库状态 | 当前无统一接口，可由后端补充 |
| `refresh_progress` | 拉取当前进度 | 当前主要来自 stdout/日志，可由后端补充 |
| `open_logs` | 查看脱敏运行日志 | 当前日志在本地文件，未提供前端接口 |

## 启动表单应考虑的参数

- 运行模式：单轮 / 指定轮数 / 持续。
- 关键词：默认值来自后端，可按前端设计允许选择有限集合。
- 城市：城市名和 BOSS 城市代码成对保存。
- 每轮页数、详情上限、岗位上限。
- 页面间隔、页面稳定等待、组合切换间隔的最小/最大值。
- 是否在启动前执行 CDP 检查。

不建议前端暴露账号、密码、验证码、Cookie、用户数据目录等凭据相关字段。

## 状态卡片应至少覆盖

1. 任务状态：`idle/running/waiting_next_round/stopped/error`。
2. CDP：端点是否可达、BOSS 页面目标数量、最后检查时间。
3. 当前目标：关键词、城市、轮次。
4. 本轮计数：`listed/details/new/skipped/errors`。
5. 数据库计数：BOSS 累计总量、启动前基线、本次累计新增、最近 `crawled_at`。
6. 停止/异常原因：登录、验证、CDP、用户停止或普通异常。
7. 日志入口：只展示脱敏日志或摘要。

## 前后端约定建议

- 所有时间使用带时区 ISO 8601；显示层可转换为用户本地时间。
- 每次运行有稳定 `run_id`，日志、进度和结果都按 `run_id` 关联。
- 进度更新应可重复读取；刷新页面不会丢失当前状态。
- 运行完成后保留最终汇总，不要把页面刷新后状态重置为“无记录”。
- 后端应明确区分“任务不存在”“任务已完成”“任务正在等待下一轮”。
- 错误信息提供人类可读摘要和可追踪的日志位置，但不回传凭据或敏感浏览器数据。
- 停止和重启应使用任务 ID/PID 绑定，避免误停其他 Python 任务。

## 当前不应对前端承诺的内容

- 采集百分比一定能达到 100%。
- 采集器能够自动登录、自动处理验证码或自动绕过反爬。
- `pause/resume` 已经存在。
- 9333 监听就一定存在有效 BOSS 页面。
- 每轮 `new` 必须大于 0。
