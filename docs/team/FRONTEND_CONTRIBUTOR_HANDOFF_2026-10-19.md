# TalentMind 前端成员接入与并行开发指引（2026-10-19）

> **用途**：供新加入的前端开发者阅读；只说明接入路径、当前技术事实、协作边界与交付要求。此文档不授予合并、数据库写入或产品决策权限。
>
> **时效性**：目前 Career Nebula 正在独立 Draft PR 开发，本文随成员交接使用。正式产品状态以 `docs/PRODUCT_DECISIONS.md`、对应提交及实际测试为准；后续用户讨论尚未回填仓库的规则，应先与项目负责人确认，不能从演示页面推定已经批准。

## 1. 从哪里获取项目

- **GitHub 仓库（公开，可直接阅读/克隆）**：https://github.com/Serena-Lyric/TalentMind
- **正式开发基线**：`master`。请从这里新建自己的功能分支，不要在 `master` 上直接修改、推送。
- **前端目录**：`frontend/`；主要栈为 Vue 3、TypeScript、Vite、Element Plus、Pinia、ECharts；依赖管理使用 `pnpm`。
- **资料入口**：根目录 `AGENTS.md`、`AGENT_START_HERE.md`、`frontend/README.md`、`docs/PRODUCT_DECISIONS.md`、`docs/README.md`；按页面需要阅读其余模块文档。
- **图谱候选仅供对照**：PR #33 https://github.com/Serena-Lyric/TalentMind/pull/33（截至本文编写，P2.2 最新已知提交 `a373427`，Draft、未合并）；P2.3 三维相机正在另一独立开发流程中，不得把未合并改动当作 `master` 已有能力。

公开仓库不意味着其中所有历史文档均为最新产品规则，也不意味着未纳入 Git 的本地私有材料可自由转发。

### 本地接入（Windows / 终端示例）

```powershell
git clone https://github.com/Serena-Lyric/TalentMind.git
cd TalentMind
git switch master
git pull --ff-only origin master
git switch -c feat/frontend-<your-page>
cd frontend
pnpm install --frozen-lockfile
pnpm run dev
```

全站非图谱改版可使用 `feat/frontend-redesign` 等清晰的分支名称；请用实际短名替换 `<your-page>`。前端开发服务器默认端口是 `18080`；`/api` 默认代理至 `http://127.0.0.1:18000`，可通过 `VITE_PROXY_TARGET` 指向隔离的开发后端。前后端未联通时应展示真实的错误/空态，不要静默以假数据伪装成功。可用 GitHub Desktop 进行 Clone、创建分支和提交；使用终端不是唯一方式。

### 向仓库提交代码

- **已有写入权限**：独立分支推送到原仓库，创建面向 `master` 的 Draft PR。
- **没有写入权限**：Fork 到个人仓库，克隆个人 Fork；将 `Serena-Lyric/TalentMind` 设为上游来源，提交到个人分支，发起指向原仓库 `master` 的 PR。
- 由仓库负责人决定是否邀请为协作者。**不要分享主账号、访问令牌、Cookie、SSH 私钥或本地项目目录的私有文件**。
- PR 必须经过代码审查、测试和用户授权后才能合并；个人开发者与 Codex 均不得自行合并或启用自动合并。

## 2. 任务范围：全站非图谱改版（已更新）

**本次成员负责整个 TalentMind 前端的非图谱界面改版，而非仅认领某一个页面。** 包含采集模块管理、JD 岗位管理、能力动态更新、简历分析、技能学习路径等业务页面，以及导航、全局布局、页头、通用视觉规范与通用组件。外观设计可以提出更好的方案，不要求原样维持旧版，但须符合项目的业务语义、品牌定位、可用性与最终产品审核要求。**未确定的视觉方案是成员提案，不自动视为用户已批准。**

| 类型 | 工作归属和注意事项 |
| --- | --- |
| 除图谱外的 `frontend/src/views/`、专属组件/局部样式、响应式布局和交互细节 | **成员的主要任务范围**；独立分支逐页改造与自测 |
| `frontend/src/App.vue`、全局导航与通用外壳、`frontend/src/styles.css` | **允许成员主导重设计**；但这些文件可能与 PR #33/P2.3 冲突，必须记录共享变更与图谱影响，并安排集成验证 |
| `frontend/src/router/` 或路由注册、通用组件与图标 | 可为全站改版调整，但不得删除/重命名 `/graph`、改变图谱路由语义或破坏登录/鉴权/注销；路由变更在 PR 中单独列出 |
| `frontend/src/components/GraphPanorama.vue`、`LegacyGraph.vue`、`frontend/src/graph/` 和图谱相机、知识点、连线、布局算法 | **不属于成员改造范围**；由 M3/M5 的 Codex 开发线负责。不得直接覆盖 P2.3 或改写图谱数据 |
| `frontend/src/api/` 共享业务契约、Pinia 共享状态 | 页面展示可以复用；涉及接口/状态结构变化先与负责人确认，避免连带破坏后端和图谱 |
| `frontend/package.json`、`frontend/pnpm-lock.yaml`、`frontend/vite.config.ts` | 新依赖和构建配置先说明必要性、许可证、打包影响与替代选项；跨 PR 文件冲突需协调 |
| `backend/`、`exchange/`、数据库脚本、冻结 DDL、真实数据 | 本次前端任务不修改；如必须变更，另提申请与审核 |

### 图谱与全局外壳的兼容契约（强制）

- `/graph` 页面仍须保持可访问、可渲染、可交互；其内部银河、节点、关系、三维相机与业务逻辑均由 Codex 负责。
- **目前仅图谱页面隐藏全局顶栏**；非图谱页面的页头可重新设计，但不可把图谱专用规则扩散到所有页面。若全站页头结构有变化，保留图谱专用容器与全屏对齐能力。
- 可调整全局侧边栏/导航视觉，但必须保留图谱导航入口、路由、页面容器尺寸约定、折叠功能及登录/注销。原有导航与图谱内部的左侧控制面板、右侧详情面板是不同组件。
- 尽量为非图谱改版使用局部样式作用域或明确的命名空间，避免 `canvas`、`aside`、`button`、`section` 等全局选择器意外改变星云图谱和弹层。
- 如需要统一修改全局外壳，成员负责外壳代码；Codex 负责图谱容器适配。双方通过可查的接口/约定协作，不允许互相直接覆盖代码。
- 不要求成员等待 P2.3 才开工；当前先从 `master` 独立开发，后续由负责人安排两条分支的共同集成验收。

## 3. 页面设计与数据要求

1. 可以整体优化非图谱页面的视觉语言、布局、导航和响应式体验，但必须维持 TalentMind 品牌识别、原业务功能及鉴权。先提出一致的组件/色彩/排版规范，优先使用现有 Element Plus / ECharts / Vue 能力，不重复引入 UI 框架；设计稿仍需产品验收。
2. 先检查现有业务 API 与 `frontend/src/api/` 契约。请求沿用统一 `/api` 与 `{code, message, data}` 格式（由请求层处理）。不为了截图效果伪造数据、统计指标或实际后端功能。
3. 页面至少有加载、空数据、失败、正常四种状态；表单具备基本校验。适配 1600×900 常用演示分辨率，并检查窄屏、长内容、滚动条与弹层遮挡。
4. 不将 M2 的离线新分析体系、B3 尚未发布的 19 项正式岗位目录、M3 候选社区算法或 M4 的演示分说成已经正式上线的可信数据。保留旧功能，不因样式调整改变业务事实。
5. 不自动开始真实采集、不更改生产数据库、不迁移旧数据；如需账号登录或联网调试，使用批准的测试环境和权限。

## 4. 跨分支集成安排与冲突预防

- `master` 当前不是完整新银河版本；PR #33 与 P2.3 均为独立、未合并候选。非图谱改版**从 `master` 开分支**，不能直接继承 #33/P2.3 的全部实验改动。
- 允许并行改造全局 `App.vue`、全局样式与路由，但 PR 应列出这些共享文件的差异以及图谱适配要求；不要求为每一项全局样式小改反复请示。
- 推荐先建立可运行的外壳与设计规范，再逐步改造非图谱业务页；将外壳和各页面的提交清晰拆分，便于测试、审查、回退和必要时选择性集成。
- 开发前、提 PR 前检查 `git status` 和 diff，不用 `git add -A` 夹带无关资产。
- **集成检查点**：由负责人在双方完成可用候选后，选择受控集成分支，合并/移植非图谱外壳与 P2.3 的图谱成果，人工解决 `App.vue`、全局 CSS、依赖/锁文件和路由冲突；进行全部业务导航、图谱容器、登录、宽高与响应式回归。合并先后次序依审核决定，不能因自动 Git 合并无冲突就跳过实机验证。
- 如果演示窗口临近而整体改版未完全完成，允许保留未经采用的页面改造分支；不为统一风格牺牲 10 月 21 日内部演示准备节点。
- 涉及后端、图谱或其他成员模块的接口变更，应先共同确认边界和责任，再分别实现。

## 5. 最小交付标准与材料入口

全站非图谱改版可以作为一个主 Draft PR，内部按共享外壳和业务页面组织可审查的逻辑提交；也允许拆分多个小 PR。交付需描述：改造范围、设计依据、共享外壳变更、全部主要页面的前后截图、启动方式、实际测试/构建结果、已知问题以及是否修改公共接口。

至少运行：
```powershell
cd frontend
pnpm run build
```

有对应测试时运行定向测试；此外在真实浏览器检查**全部非图谱页面**的导航、业务操作、输入、长内容滚动、窄屏和错误状态，并在实际集成分支上复验 `/graph`、登录、注销及全局外壳。测试没有执行就明确写未执行，不得编造通过记录。

给成员提供材料时，优先发**已审查的 GitHub 文档链接、确定提交或 PR 链接**；本地私有材料只通过负责人批准的渠道提供脱敏导出件。不要将 `.env`、API 密钥、真实简历、Cookie、数据库文件、`input/`、`output/` 或未入库原始资料提交公开仓库。
