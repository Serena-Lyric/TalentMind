# 工作候选纠正、旧观察重放与版本分账

## 症状

P3 在用新 P1 分析明确纠正关系后，再次提交旧分析，旧来源被重新列为 pending，候选无故增加版本并再次要求重评。来源都可回溯，但“已明确替代”和“尚待选择”被混为一谈。

## 根因

自动观察只检查新来源是否等于当前分析/待决列表，没有排除已经 superseded 的分析。保存历史并不自动保证重放不会恢复旧疑点；同样，重复字面命中也不能恢复已撤回关系。

## 修复

- `pending_analysis_sha256s` 与 `superseded_analysis_sha256s` 分别存储；旧 superseded 观察重放只记录批次观察，不重开未决或增加候选版本。
- 更换有效分析须用 `correct` 绑定基线旧关系摘要和同 JD 的新范围；旧来源仍可读取。自动检索不会覆盖已有关系，撤回/拒绝不因重跑复活。
- 批次绑定 registry ID、revision 和快照 SHA；比较和纠正均基于同一旧版本，不读取半批更新。原始分析、知识与审核材料按各自摘要冻结。
- 回归先重现旧分析重放造成变化，再验证修复后关系/候选逐字段相同；CLI 另覆盖提交前强退回滚及提交后输出丢失的精确重试。

## 教训

幂等不只指同 batch ID 重试，还应覆盖旧观察在后续批次的重放。历史来源、当前依据、待决新版本及已替代来源必须分开，不能让旧证据反复回流改变当前状态。哈希/引文校验只证明定位和版本，不证明语义、人审身份或独立来源。

测试使用临时独立 SQLite，finally 删除并核对目录不存在。Windows 下 `with sqlite3.connect(...)` 只处理事务，不关闭连接；测试也须显式 close（或 `contextlib.closing`），否则临时库删除会因文件占用失败。
