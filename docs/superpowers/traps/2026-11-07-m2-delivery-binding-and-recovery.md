# M2 集成：运行依赖、跨库提交与冻结来源

## 症状

- B3-5 冻结候选仍指向不断修改的产品文件，严格来源摘要与引文验证在本地及 LF checkout 两项失败。
- 新入口的候选阶段失败后，已提交 P1 不易经消费者读取；受控 `not_run` 和空识别还曾分别计成 failed/complete。
- 提示摘要随模块导入固定，但 P1 每次调用实时读提示文件；长驻进程可能在磁盘提示变化后继续复用旧事实。
- 默认 P1 完整 run 的顶层请求可能是 audit，仅按顶层登记缓存会遗漏 primary。

## 根因

可变产品页面不能作为永久字节证据。P1 全局 outcome 包含 classification=not_run，不能直接作为已执行五维的完整率；执行失败、语义无结果和根本未执行不是一类。运行账本与 CandidateStore 分属两个 SQLite 事务，写结果/更新候选/导出必须分别设计恢复。已加载源码与实时读取的文件也有不同生命周期。

## 修复

- 原 `candidates.v1.json` 与 SHA 不改，新 `draft-source-v2` 指向 Git `26deedc6` 的精确不可变来源，保留原引用和候选性质；旧 SQLite replay 读取已冻结原字节，新版本不继承批准。来源仍严格校验，拒绝篡改与越界。
- 每条分析、primary/audit、进度和最终结果只追加；P2/候选失败仍可读取有效事实。P1 五维、execution、全局 outcome 和候选阶段分别表达；not_run/unknown/partial/failed 分账，空识别不当充分缓存。
- 候选 batch ID 由 run ID 摘要生成，冻结旧基线和请求。候选已提交而最终账本未提交时，精确重试读回同一版本；别的 run 先推进则拒绝过时请求，不悄悄重基。导出失败后直接读原最终结果，不重新调用模型或演化。
- 写者用既有 OS Lease；读历史用只读连接。`run_id/request_sha256` 校验选中运行，旧结果不从当前 candidate head 或新知识重建。
- 运行前/候选提交前核对磁盘依赖与加载绑定；提示/源码漂移拒绝继续，重启后另建新 run。已结束历史读取不依赖当前代码。记录回放递归收集完整 P1 的 primary/audit，仍按精确请求 SHA 匹配，不做近似替代。
- 评价先校验签审条件与 annotation 原字节，重复样本拒绝；未诊断与明确 unknown 单独给覆盖数，A/B/C/D 分组。Agent 诊断与原文跨度提示不产生独立人审分数。

## 教训与验证

测试必须穿过实际入口、真实 SQLite 与子进程提交边界。`test_delivery.py`、`test_delivery_cli.py` 覆盖停止/取消、条目和候选提交前后 `os._exit`、导出失败、重复、过时请求、只读并发及实时提示变化；`test_delivery_evaluation.py` 覆盖实际 CLI/批准绑定、篡改/重复/错误 run 拒绝。临时夹具 finally 精确移除，持久化演示证据独立私有保留。独立真值不足仍是未验收，不以绿色测试或缓存重编译替代真实效果。

全仓复验还暴露 Windows 测试夹具的两个边界：`tempfile` 可能返回 `SERENA~1` 短路径，签审发布保护要求显式路径等于其 resolve，应在合成测试夹具中使用规范化路径，不能放松生产校验；PID 文件存在也可能尚未写完，睡眠 worker 测试改为临时文件写完后原子发布 ready 文件，不修改真实采集实现。

干净 Windows worktree 还重现了已发布 P2-1 `knowledge.json` 被 autocrlf 转换后与 manifest 摘要不符。按不可变资产路径固定 LF 检出，而不是修改 manifest/归一化后再校验。必须验证真正的新检出，原工作目录恰好为 LF 的绿色测试不能证明跨平台可重放。

首次全仓 Linux CI 的 Windows 浏览器查询测试虽替换了进程查询，仍进入真实 Windows 平台门禁。该单测在非 Windows 时补齐 OS/无引号合成 argv 边界替身，保持完整输出断言；Windows 仍走真实原生 argv 解析。不能为了离线测试削弱浏览器生产门禁，也不跳过该断言。

Windows 全仓高负载下，即使 PID 已原子发布，短暂文件共享占用仍可能让读取报 PermissionError。就绪条件改为限时内成功读到合法数字；只重试尚未可读的测试夹具，不吞超时或生命周期断言。单次定向绿色不能替代并行负载下的完整复验。
