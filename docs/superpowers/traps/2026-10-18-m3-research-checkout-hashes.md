# M3 研究：原字节摘要与 Git 文本换行

日期：2026-10-18。

## 症状

研究最初把本机正式快照的 SHA `6565…` 硬编码进新测试；在 Windows 通过，但只读检查发现 Git blob 摘要为 `e8e3…`，LF 检出会失败。同样代码跨检出的完整实验摘要也会因来源原字节变化而不同。

## 根因

本机 `core.autocrlf=true`，Git 保存 LF，工作副本为 CRLF。两种字节序列代表同一 JSON 内容，却有不同 SHA-256。把原字节身份与文本检出一致性混为一个哈希，会错误宣布数据被改动或破坏旧证据。

## 修正

- 不改正式 graph.json 或已有 `6565…` 证据；运行前后仍按实际字节 SHA 核查。
- 新研究记录原字节来源 SHA，另增加明确的 CRLF→LF 文本摘要和 portable 比较摘要。
- 新快照测试固定核查 LF 内容摘要，仍断言原文件前后字节不变。
- 合成空图通过真实 CLI 分别输入 LF/CRLF，验证原字节摘要不同而 portable 相同；固定软件/源码后做独立进程复算。完整快照复算不覆盖旧结果目录。

## 教训

证据原字节 SHA 不因环境便利而回写。文本规范化只用于附加比较，须声明规则与范围，不能把它当成不同输入内容或不同原生库版本完全等价的证明。研究计算过程中修改源码也必须拒绝发布结果；本轮曾实际触发这一保护，并保留为失败执行记录。

此处不修 M2 候选目录因产品主文档变动导致的旧来源摘要失效；那是独立的证据版本问题，已在本轮阶段报告登记基线复现。
