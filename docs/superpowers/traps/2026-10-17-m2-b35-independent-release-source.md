# B3-5 审核与发布来源不能互相冒充

日期：2026-10-17。仅合成临时目录复现，没有真实目录发布或生产写入。

## 症状

初版允许复制审核依据为另一个路径后当作独立 release 确认。自查修复后，独立 reviewer 又发现审核事件 JSON 自身也可复制成确认来源，合成模式得到 admitted；真实模式只得到待授权提案，formal_jobs 始终为空。另自查发现事件/manifest 二次读取存在解析内容与已保存原字节不一致窗口、相同 release revision 可命名不同 manifest。

## 根因

只排除审核引用来源路径，未覆盖来源副本、审核事件原输入及历史事件；用路径不同代替独立来源。两次读取同一个路径，无法保证保存与解析是同一版本。发布版本只有字段，没有不可变摘要绑定。

## 修复

自查五项与独立审查两项负例先 RED 再 GREEN：排除所有本快照审核来源及事件输入的路径和原字节 hash，包括完整记录序列化副本；独立确认引文必须指向具体候选、完整定义 SHA 与快照 ID。原输入只读一次并解析保存字节；命名 release revision 事务绑定 manifest 摘要，修改须新版本。候选、审核、发布提案与合成 admitted 均独立保存，正式文件零条。

## 教训

身份/授权真实性无法靠姓名、文件路径、hash 或格式证明。结构门禁应尽可能拒绝明显的来源复用，但任意修改/伪造文本仍需现实逐项确认和受控 PR 审查。合成完整状态机只验证程序，不是用户批准职业定义。

## 补充：跨平台来源字节

收尾新用例先复现 LF 干净检出无法匹配 Windows CRLF 产品文档摘要。根因是 Git autocrlf 在不同平台改变工作树原字节，和强来源 hash 绑定冲突。仅对当前已修改、作为定义依据的 `docs/PRODUCT_DECISIONS.md` 设置 `text eol=lf`，将该文件规范为 LF 并重新绑定候选来源 hash；不放宽原字节验证，不改变历史 family/DDL。干净 LF 用例由 1 failed 转 GREEN，专项 75 passed。带原字节指纹的仓库内发布资产必须有确定的 checkout 编码/换行约束；其余实际源码字节差异继续保守形成不同分析依赖版本。
