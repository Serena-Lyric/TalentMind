# 采集动作中断与显式恢复

## 症状

控制台历史任务已经结束，再次准备浏览器仍报 `collection_action_unfinished`。页面冷却已到期，私有频率账本中仍保留该平台的动作标记。

## 根因

`run_action()` 在浏览器动作前提交预约及 owner 标记，再取得写事务锁并复核 owner。正常结束时提交完成时间并清除标记。回调异常或进程退出会留下已提交的标记，旧版本只有拒绝后续动作的路径，缺少可核查的恢复入口。任务结束和浏览器动作完整结束是不同事实。

## 修复

`frequency_recovery.py` 提供独立状态读取和显式恢复。控制台 API 沿用本地原文访问边界，恢复与准备、单项、批次及桥接任务互斥。

恢复事务使用与浏览器动作相同的 SQLite `BEGIN IMMEDIATE` 写锁，精确核对 owner。正在执行的 callback 持锁时拒绝恢复。若恢复先于尚未执行的旧 callback 获锁，旧 callback 随后的 owner 复核失败，无法执行页面动作。异常回调记录已退出的证据，历史标记及进程退出保留 unknown 分类，两类都通过显式操作恢复。

恢复保留原预约时间的审计回执，页面冷却从恢复时刻重新等待 30 秒，存在已知搜索目标时组合冷却至少等待 720 秒，较长的已有余量保留。相同 owner 重复请求幂等，新 owner 出现后拒绝旧请求。账本损坏、时钟回拨和写入失败保持关闭，事务失败完整回滚。

## 教训

恢复操作应复用实际动作的排他锁及执行前身份核验。仅凭任务完成、冷却到期、PID 缺失或按钮确认不足以处理预约与执行之间的竞争。状态读取、恢复与实际采集分别提供入口，恢复成功后仍由用户重新准备和启动。

验证使用临时 SQLite、合成时钟和独立解释器中的合成动作，覆盖 callback 异常、`os._exit` 进程退出、活跃跨进程 writer、预约间隙 fencing、重复恢复及回执失败回滚。未操作实际频率账本或真实平台。
