# M2 P1：机器草稿、有效部分与真实语义边界

## 症状

云端返回合法 JSON 仍可能把条件排除解释为“不要求”、把共现/同名工作升为明确用途、把开放举例强制全部满足。真实 DEV 还出现了把章节名 `requirements` 当作输入字段而导致整组要求拒收。工程审查复现了坏 `kind=[]` 中断整条、私有输出可写公开目录、全失败/未执行返回成功及坏 manifest 根类型抛 traceback。

## 根因

- 语义理解、来源定位、结构合法和人工确认是不同层次，不能凭引文存在或推理强度高推导效果可靠。
- 单项访问在异常隔离外、保存入口缺私有路径保护、粗略的 partial 汇总掩盖了全部失败。
- 长驻 worker 每条重读磁盘文件计算版本，会把已加载旧代码错标成后来编辑的新版本。

## 修复

- 新入口独立于旧 B1/B2；模型主理解、程序逐项证据和契约校验。坏项降覆盖并保存其他有效项；截断不补 JSON。
- 字段使用实际非空输入 Schema。只有字段缺失/空且全文存在逐字唯一引文，才透明改绑 `raw_text` 并记录调整；不做空白/字形规范化或歧义猜选。
- 类型检查放入单项边界；复用 `safe_destination` 限仓内输出到 `data/local`；失败、未执行及坏根类型走安全出口。新 run 独占目录、manifest 最后写，不覆盖历史。
- 载入时固定源码摘要，提示/输入/配置另行绑定；显式补充 `refine` 绑定旧分析和原文版本，保留原始执行状态、费用与新旧结果，不将补充结果自认人工通过。
- 不因一个正向程度字段不是连续原文而丢整项能力：完整陈述/证据保留，结构化程度暂未解析并降覆盖。既有 claim 证据能逐字支持限定词才扩 scope；仍须另审限定词归属。负向程度、无法回源的条件不删除救回，防止扩大/反转要求。经验对象不保留技能类别，原草稿及调整均可审计。
- 最终编译器可使用原真实模型回包重编译，但必须核对原请求摘要、origin run 原字节摘要并单列原 API 时长/用量；缓存编译耗时不是新模型延迟，Token 不能重复计费或冒充新模型验证。
- 首轮独立 Review 发现字段级编辑器仍可把“整段包含限定词”当作限定词属于当前要求，也能让同名/共同对象关系自报为 explicit。修复改为限定词 target/qualifier/局部谓词或明确承接的成对证明；同名活动、共享上下文和共现分别封顶为 inferred/unknown，只有正向前提下可回源的“使用某手段完成某局部工作”才可 explicit。
- 后续反例又复现了三类绕过：短实体名匹配到更长技术名、审计静默清空已有 degree、以及用逗号把前一动作的工具接到后一动作。关系 object 与 action 必须在同一真实局部子句对齐，ASCII 实体边界和兼容字形回映射都要校验；已有 degree/condition 不得被静默擦除。逗号后新增独立谓语、对象或第二个工具时必须拒绝或要求明确承接，不能只因文本先后顺序升级。真实“运用方法，定位问题”中分隔符后直接接同一局部工作则仍需保留，避免防卫过度。
- 审计从空关系集重建时，“模型未返回”不等于“确认删除”。必须逐端点检查审计是否处置了全部既有关系统；遗漏任一端点时记录审计问题并降 relations coverage 为 partial，不能让合法但不完整的关系补丁继续报 complete。真实回包覆盖全部端点并不能替代这条程序不变量。
- 最终反例又发现四类组合/关系绕过：`未用于/不会用于/并非用于/不是用来` 等后置否定仍可被当正向用途；`cooccurrence/unknown` 可被新增成任意矩阵；`same_activity` 自报加两个端点引用也能铺满职责×要求矩阵；量词从同一 scope 的无关句子取证。修复要求后置否定进入局部用途守卫，新 unknown 仅允许既有端点，完整笛卡尔积无论关系强度均拒收并降 partial；组合量词只在同时覆盖全部成员的局部句生效，否定式“全部/每项”不能证明 all_of。
- 第二轮 Review 证明“两端各有引文”仍不足以建立 inferred：没有 `means/work` 的 same_activity/shared_context 只是模型标签加共现。修复后新端点不生成关系，既有端点最多降为有界 unknown；只有完整局部工作锚点才可 retained inferred。真实模型还省略了嵌套 requirement.reason，外层 reason 可确定性回填，但其他结构、引文和限定词证明不得随之放宽。
- Flash-1017 迁移反例表明：动态 Locator 字段列表会破坏 system prefix，缓存命中必须使用固定 Schema 并在后续 user 内容放 JD；JSON mode 仍可能在 HTTP 200/`finish_reason=stop` 下返回缺括号内容，不能补写或伪装成功。只允许在保留原失败后做一次同配置、同输入诊断重试，再次失败即停止，无 Pro 回退。软性章节状态必须在下一明确程序标题处截止，共享产出不能因拆分 preferred claim 而丢失 AND condition。
- 第四次 Review 再次证明“共享同一个长 scope_evidence”不等于共同约束：independent preference 即使被同一条证据包住，也不能自动成为另一个要求的 condition。只有选择项与产出同处一个局部句、且没有被“也优先/另外/此外”等独立偏好标记分开时才允许连接；申请材料证明也不是天然 experience，现有枚举表达不了时应保留 unresolved，避免把申请阶段误当资格条件。

## 教训

模型、提示、字段校正和补充调用都须以实际 DEV 的全体适用单位和 A/B/C/D 对照评价。保守未知不能覆盖明确事实；更长提示或更高推理强度也可能引入回归，必须统计漏提、误提及关系等级错误。程序守卫要同时覆盖拒绝坏证明和保留真实直接用途，并用正反例成组回归。工程回归见 `test_understanding*.py`；当次真实结果与未解决项从总进度表进入报告，不能将本陷阱当阶段验收通过。
