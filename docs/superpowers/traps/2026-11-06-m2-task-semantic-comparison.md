# M2 任务对照：提议、出处与语义判断分开

## 症状 → 根因

原始模型 JSON、合法 ID 和真实引用通过校验，仍把维护、教学材料、评测或准备文档当作程序开发。
出处存在不能证明动作/对象语义相符，整批自由选择还可能混淆任务 ID。无职业目录或工作事实时，
统一写 evaluated 又把未执行评价伪装成已判断未知。

## 修复

- context v4 将原始提议留在研究 trace，不加入业务轴候选/召回。family/canonical 依据各自
  参考和职责事实标明未执行；技术轴独立使用实际 duty/goal。历史 v3 不被重写。
- 显式 evidence 路径对给定职责—任务分别核对动作、对象及实际执行；模型不能自行选择身份，
  不能把为他人提供输入、目标或同流程关系升级为本人行动。双侧短引、模型响应和失败均保存。
- 单独绑定每个提议、选择、实际检查、待执行与预算外范围；分数只用于优先级，不作支持概率。
  每角色的 pair 预算必须真的计 pair，不能暗中限制为每 claim 只看一个任务。
- 动作和对象分别有出处仍可能拼成假工作。要求同一版本化工作范围与合格来源作用域，
  不跨独立工作借对象；共享对象的裸谓词协调和“参与”词内边界另做回归。
- 机器支持进入独立 work_candidates，仍 machine_unreviewed；不选择主岗、清除 gap、
  确认正式职业或反写 P1。具体参考任务不相符也不是正式职业排除证据。
- “实际执行”过度表述曾让模型把职责当已完成履历，甚至把更具体的软件实现当辅助。改为本岗直接
  责任和具体子任务，仍不能把过程准备材料当对象本体。v3 的正向判断增加对象类型单独问题，
  对象仅来自别人目标后件也不准借给本人动作；同模型复核不冒充独立人审。
- 早期输入/源范围判定和旧对象字段形状保留，读取不按新规则重判或补写默认空字段；源码、提示、
  对象问题和实际新推理分别绑定，不将回放说成 fresh。
- 序列化 schema 若按字母排序，会改变 llama.cpp 的生成顺序，让模型先决定标签再寻找引文。
  运行器保留调用方的属性顺序；任务响应先生成双方引文与短理由，再给判断，对象检查先理由后关系。
- 重复动词不必一律失去引用位置。仅在动作/对象都属于同一合格工作范围且定位范围唯一时联合选择
  引用位置，优先不相交的最短覆盖；不同工作范围仍不猜测。历史读取只校验保存位置，不重新定位。

## 教训与验证边界

过严的实际执行定义会把真实软件实现误拒为辅助；出处检查再多也不能替代真实正反例评价。
旧模型、模板、成对提示、检索预算与源工作范围变更分别分账；不能把重解释或回包重放称新推理，
不能把 Agent 诊断称人工真值。新的模型/任务检查也必须报告错配和遗漏。

专项入口为 `backend/tests/test_job_analysis/test_knowledge_task_comparison.py`；
真实 DEV、失败记录、模型来源与 CI 见 [Issue #63](https://github.com/Serena-Lyric/TalentMind/issues/63)。
