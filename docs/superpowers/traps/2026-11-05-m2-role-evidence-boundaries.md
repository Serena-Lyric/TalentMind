# P2-2 局部责任、交付与历史契约边界

## 症状

- Windows 干净检出后，P2-1 知识加载报 `knowledge digest mismatch`，原专项 62 failed / 146 passed。
- “如果客户需要，开发软件服务并交付应用”把条件后件当成无条件主岗。
- 同一 P1 claim 的其他职责为软件候选借出交付或技术；“并/以及/同时”与标点采用不同的局部分组边界。
- claim 内一个辅助分句让其他核心职责也被解释为辅助；单个“岗位1”编号被判成多职位广告。
- 历史结构只核对行级原文，允许换 claim 类型、夸大 core、改变嵌入定义或让主岗与四轴矛盾。

## 根因

Git autocrlf 改了已按原字节绑定的知识文件。业务解释把 claim 当作最小责任/交付关联单元，
实际一条 claim 可以包含多个工作；逗号、并列连接、方法词和辅助词的作用域不完全一致。
有来源行和 manifest 并不能证明支持属于指定 claim、原始定义和重要性。

## 修复

- 对 `knowledge/catalog/**` 与 `knowledge/policies/**` 固定 LF；恢复 Git 里的原知识字节，
  不重算旧 manifest 或放松摘要校验。原 208 项基线恢复通过。
- 职责支持要求 P1 文本及实际局部原文同时满足有界动作/对象规则；条件检查保留实际字段中
  的语句范围。教学本身可以是正向边界职责，不能全局屏蔽教学而假称否定处理正确。
- 工作分组与局部谓词采用一致的连接和方法词边界；交付/技术只关联同一工作片段。
  辅助词按片段解释，未解释核心工作单列；不改写原 P1 claim 或 core。
- 多职位编号至少需要两个不同目标；所有身份操作保持 none。
- 结果嵌入原知识 JSON、事实和版本化规则，校验知识原字节 SHA、定义及来源一致性。
  支持必须绑定正确 claim 种类和其证据范围；core 不能超过来源 core，主岗须与岗位轴及
  核心证据一致。历史读取只核结构和版本绑定，不用当前算法重新解释旧结果。

## 教训与验证边界

检索线索、局部规则支持、机器语义与人工真值分别表达。P1 claim ID 是事实身份，不能作为
所有内部谓词自动相关的证明；行级引文存在也不能取代局部作用域。
新增反例先观察失败再修复；测试路径为 `test_knowledge_attribution.py` 和
`test_knowledge_attribution_io.py`。实际计数、DEV 效果、首轮记录及 CI 见
[Issue #63](https://github.com/Serena-Lyric/TalentMind/issues/63)。
有界规则及五个候选参考仍存在中文改写/目录覆盖限制，合成测试不能证明市场准确率；
没有独立四轴/完整检索真值时指标为无法评价，不把未决记为正确，也不发布正式职业。

## 四轴和混合形态的独立性

**症状 → 根因**：仅支持某个岗位参照的 duty 才进入 track 检索，导致目录缺口抹掉真实技术使用；
只有一个 family 弱候选也返回 mixed，导致证据不足被误写成混合岗位。

**修复**：解释版本 2 的 tracks 单独对账 P1 实际技术工作及源引文，绑定局部手段—技术名—工作；
仅有要求/技能列表、培训、条件/否定不确认方向。来源技术名允许受限候选，不发布正式方向，
也不以已有职业支持为前提。单一不足复用 unresolved；mixed 需要不同方向及独立工作片段，
并列核心保留 parallel。旧解释版本 1 原样读取，修订结果另存。

**教训**：四轴独立不表示只看技术名。放开角色依赖后仍须防“使用 Python 整理资料后使用 Java 开发”
借手段和“系统开发培训”变成研发；共享谓词不能把后续辅助工作并进前一项证据。
反例在 `test_knowledge_attribution_review.py`；45 组真实对照的逐例诊断仅作为 Agent 审计，
引用人工职责不使职业映射自动成为新增人审真值。源码/策略/参考变化分开报告，不拿新增局部支持冒充市场覆盖。

Windows 证据路径使用 `Path.parent` 等路径 API；不要通过替换 `/value.json` 取目录，反斜杠路径会留下文件名，导致历史读取把文件当目录。

## 局部未知、裁剪引文与模型候选

**症状 → 根因**：所有职责 core 必须已知、同片段必须出现交付动词，使局部可靠工作被全局门禁抹掉。
双重词表要求还将 P1 转述差异当成原文不支持。“不同/不断/未来”被否定字的子串误杀。
只检查裁剪 quote 又会漏掉同源句前面的“不负责/无需/客户负责/曾经”；“同时”也不能解除共同作用域。
一个短工作命中不能解释整段并列任务，教学的后置修饰不能冒充本人软件交付。

**修复**：显式 context 路径把原引用工作、重要性、局部支持、目标上下文和主岗充分性分别保存。
检查原字段中的支配前缀，区分同分句否定与明确独立主体，不因裁剪或并列词清除条件。
模式未解释的核心/重要性未知片段仍阻止主岗，已有局部支持不丢；无交付原文仍留空。
所有来源派生的技术、交付和上下文也遵循作用域，避免只清理 supports 留下矛盾结论。

**症状 → 根因**：本地 NLI 给主体/条件/教学硬负例很高蕴含分；生成模型可输出看似合理却不存在的任务 ID。
仅给候选标 basis 也不够，篡改 basis 可伪装来源；加载后模型/运行时文件变化会让执行与记录 SHA 不一致。
历史读取重新构建当前提示词，则旧提示词版本变化会破坏历史读取。

**修复**：拒绝以 NLI 分数确认工作；生成模型仅提出独立弱候选，不能选主岗或消除 gap。
模型解码只能选当前存在的工作与参照任务，保存再查双侧来源、重复项、scope 和候选强度。
模式候选也必须绑定实际 comparison support，不能靠自声明 basis 绕过；执行前复验文件 SHA。
模型固定输入、当时提示词/响应和版本保存，历史读取只校验保存内容，不执行当前提示词生成器。
非法/超时返回可观察失败，保留其他局部结果；具体运行证据只在 Issue #63 记录。

**教训**：语义候选增加不是正确率提高，模型理由可审不等于理由正确。正反例、真实开发集、
人工职业真值和运行失败必须分别对账；复杂中文仍有局限，不以测试数量完成业务验收。
专项入口为 `test_knowledge_context.py`、`test_knowledge_local_semantics.py`。
