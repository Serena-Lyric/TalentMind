# M2 真实职责、章节与语义作用域

## 症状

真实 120 条主集中 B1 大量 `insufficient_evidence`、B2 超过千条 `uncertain`、B3 没有大类候选；但原文里存在明确的“负责系统开发”“熟悉 Python”“负责数据仓库 ETL”等表达。直接扩展正则又会把“开发进度管理”“工具采购”“公司研发系统”和纯经验要求误当当前技术职责。

## 根因

1. 只覆盖“动作在对象前”的中文句式，未覆盖“对象 + 设计/开发/测试/部署”。
2. B2 将任意位置的条件词应用于整份 JD，并在没有技能的学历/年限句后丢失任职要求章节；同一句多个技能、未知同级项和共享尾注又容易被拆错。
3. B3 只有极少数完整交付句；放宽后公司背景、要求列表、标题和来源章节错配会生成假候选。
4. `duties` 与 `raw_text` 经常重复同一职责，若只按出现次数会增加统计噪声。

## 修复

- B1 只在当前岗位职责出现明确动作/技术对象关系时确认范围，并排除进度、采购、工具、流程、管理、任务、需求等对象后缀。
- B2 将普通风险词限制在当前句；只有“仅适用于”等显式记录级条件和“以上技能/满足一项”等显式尾注跨句生效。章节内无技能句保留章节，不再默认重置为未知；结构化字段优先去重。
- B3 只接受编号/明确职责章节中的动作与技术对象，要求或公司背景不能生成候选；竞争候选保持 `pending_review`/`unresolved`。
- 人工复核使用只追加事件并绑定机器结果 SHA-256，机器结论、原文和历史报告不改写。

## 后续审查修复

`section_capability_extended` 不能因一个明确能力动词就把带开放或限制尾注的单技能升级为必备。“熟悉 Python 或其他技术”“熟悉 Python（非必备）”“属于可选要求”“非硬性条件”均保留 `uncertain`；同时继续保留普通补充职责和明确组合规则。该修复在同一 120/60 冻结样本上的 `v10` 与 `v9` 指标、逐条状态和证据数量一致。

## 教训

“减少 uncertain”不是直接放宽句式。必须先区分章节、要求对象、条件作用域、否定/组合和来源数据章节错配；可回源、保守未决和可人工复核比虚假确定更有价值。
