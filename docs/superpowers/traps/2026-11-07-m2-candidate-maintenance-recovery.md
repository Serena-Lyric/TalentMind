# M2 候选维护：冻结基线、恢复与来源

## 症状

候选页面可能使用旧版本提交；响应中断后重复点击或刷新，可能重复写入或丢失恢复请求。技能候选的新证据若已被 runner.observe 绑定，再调用 revise 会因“没有新证据”失败。岗位研究接入 delivery 后，独立 CLI 可成功但恢复路径报嵌入知识摘要不一致。

## 根因

- 工作批次、技能文件和网页请求有不同的提交边界，只有前端内存请求 ID 无法覆盖进程退出和刷新。
- 运行准备后已冻结候选基线，旁路维护会使恢复变成重基而不是重试。
- 已绑定观察与未绑定新来源具有不同含义；旧 run 和当前候选 head 不能混读。
- LoadedSnapshot 只重建解析对象而丢失原始字节时，重新序列化不一定等于原文件 SHA。
- 技能版本和投影已经发布，但最后回执写入失败时，旧门禁仍把“读回已保存成果”当作“重新执行语义操作”，部署变化导致pending永久挡住新run；原意图还没有绑定原投影和完整响应，不能安全认领现存投影。

## 修复

维护复用 DeliveryStore 的 OS 写租约，校验 baseline/候选版本/关系摘要；未完成运行与维护相互阻止新的状态写入。维护意图和最终响应持久化；工作批次依赖原事务幂等，技能版本通过同父目录临时文件完整写入后原子发布。重复请求返回原保存结果，过期请求返回 409。页面刷新后可读取 pending 命令并显式恢复，不能通过重新生成请求 ID 绕过失败。

显式维护关闭自动关联应用，避免给候选 A 选择来源时同时修改 B/C；该执行模式纳入批次摘要。准备后尚未提交的维护必须匹配原算法依赖，不能部署新代码后悄然用新规则执行旧请求；已提交工作批次仍可按原摘要精确读回。

技能修订从服务已保存的分析中筛选同解释、尚未绑定来源；已 observe 材料排除，不把自动观察改成逐条人工审批。历史候选版本只显示该版证据，当前投影另标 current_head；历史 run 始终保留原投影。冻结知识恢复时同时传递原始字节和摘要。

F4修复将目标候选、预计算投影和完整响应一起写入准备事件，再原子发布候选和投影。恢复分别核对原文件manifest、候选内容与投影摘要；全部发布完成只补原回执，可跨依赖变化，无须运行当前算法。任一未发布仍检查原依赖；损坏不能通过重算伪装恢复。旧意图在原依赖下可生成明确的materialized绑定；跨依赖时没有绑定则只允许用户显式结束，追加`maintenance_closed`并显示`closed_incomplete`，保留已写成果，不能写成rejected或成功result。

检查产物不能只遍历目录：已发布版本或SHA路径若损坏为普通文件，按`is_dir`过滤会把它误当作未提交。旧版结束入口必须显式核对目标版本路径，并按SHA名称选择投影后验证类型、路径及manifest；损坏时保持pending。

## 教训与验证

事务性正确还须检查文件发布、最终响应和浏览器刷新之间的窗口。测试覆盖 commit 后异常、精确重试、旧版本并发提交、未完成运行、恶意 Origin、历史新来源 revise、撤回后下一批对齐；合成浏览器操作补充真实控件提交/刷新与两页面冲突。所有夹具使用独立临时 SQLite/文件，不访问正式库；故障测试不以清空原库恢复。

F4回归还覆盖候选发布前后、投影原子发布刚完成及最终回执失败，模拟依赖更新并把当前解释/投影函数替换为失败断言，证明精确恢复不重算；旧版显式结束的HTTP门禁、空原因/多余字段、重复原因、持久读回、禁止再恢复及新run解锁均单独测试。此程序验证不等于新的真实模型、生产数据库或浏览器验收。
