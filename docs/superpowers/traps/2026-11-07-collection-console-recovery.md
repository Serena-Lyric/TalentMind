# 采集执行状态、结果与恢复入口

## 症状与根因

- 任务 `completed` 被统一显示为“已完成”，即使事件全部拒绝、实际写入为零，也缺少直接的结果摘要。
- 准备失败消息优先显示，显式刷新取得新浏览器证据后仍能残留旧占用错误。
- 频率账本中的未完成动作只能通过原始异常发现，页面缺少只读诊断及显式恢复入口。
- 数据库缺列直到启动后才暴露，启动按钮未反映当前写入条件。

## 修复

- 显示“执行结束”，同时展示实际新增、更新、拒绝、失败和跳过结果。历史未知字段保留未知，部分计数已知时逐项展示。任务结果抽屉与重新准备分别由按钮触发。
- 显式浏览器刷新替换过期准备错误，同时保持重新准备的要求。状态请求使用递增序号，开始提交时及成功返回时使旧状态响应失效。
- 公共诊断区读取各平台频率状态。恢复提交服务端给出的 `recovery_token`，重复点击互斥，迟到读取失效，恢复成功与失败后都重新检查。页面展示冷却时间，恢复后由用户重新准备和启动。
- 写入条件显示具体缺列及下一步。数据库检查失败显示无法确认，阻止单轮和批次启动。浏览器准备、批次计划与桥接会话创建继续可用，桥接实际采集由后端检查。

## 验证与教训

新增 10 项回归执行实际 SFC setup 与编译模板事件，使用合成 API、隔离计时器，覆盖全拒绝、部分写入、空结果、未知计数、缺列、读取失败、恢复冲突、重复点击、迟到响应、历史切换和卸载。该验证范围为组件行为，真实招聘平台采集需另行验收。

执行状态、持久化结果、浏览器访问证据与数据库写入条件应各自有明确来源。更新一种状态时，需要核对其他操作是否仍持有过期证据。
