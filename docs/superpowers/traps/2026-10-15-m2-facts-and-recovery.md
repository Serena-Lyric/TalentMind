# M2 输入、事实提交与发布恢复

日期：2026-10-15。涉及阶段 A 独立基础层，不表示旧管道已修复或生产已切换。

## 症状

历史评估发现旧状态层仅比较正文前 2000 字的 SimHash，force 保留旧字段，续跑聚合漏历史事实，按岗位组验证可能串用其他 JD 的引文。阶段 A 的发布失败回归另外发现：恢复默认聚合版本可能把原运行 v2 悄悄重建为 v1；只留 facts_committed 也无法说明文件写出失败。

## 根因

输入身份、输入内容、执行状态、证据有效性和聚合发布共用旧阶段语义；版本与运行成员未被固定。SQLite 事务结束与输出文件成功不是同一件事；`sqlite3.Connection` 上下文退出仅提交/回滚，并不关闭连接（Windows 临时库会因此无法删除）。

## 修复

- 新建独立 foundation，不沿用旧状态/去重/验证行为；完整字段确定序列化 SHA-256，来源身份与观察单独保存。
- 单条不可变快照绑定每次尝试与逐项 claim；程序核对本 JD 的完整引文，不能将 matched 解释为语义正确。
- 运行事务固定完整成员与分析/聚合版本；事实和终态同事务提交。遗留 running 变为 retryable，成功事实复用，恢复不读取后续运行的新 heads。
- 聚合先持久化；文件同目录暂存、fsync、原子替换后才完成。文件失败记录 publication_failed/artifact_publish_failed，resume 沿用原聚合版本；版本不符拒绝恢复。
- fixture 使用 finally/显式 close，关闭后删除其专属临时目录并断言不存在。八个位置的 `os._exit` 子进程测试覆盖数据库、聚合、暂存与替换后的恢复。
- 独立审查补强：拒绝硬链接状态别名，防止不同旁置锁误恢复活跃进程；终态 attempt 禁止 INSERT 新事实；store 开启 recursive_triggers，阻断 REPLACE 隐式删除绕过不可变触发器。归一化使用与本次版本清单相同的一次读取词典快照。

## 教训

API 成功、引文匹配、任务完成与统计资格必须分开。用实际硬退出和文件失败验证恢复，不能只看状态字段存在。SQLite 与文件系统之间采用可恢复的发布协议，不能提前宣布整轮成功。旧库仍隔离，旧缺陷不因新入口完成而自动消失。
