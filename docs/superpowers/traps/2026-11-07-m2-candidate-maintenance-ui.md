# M2 候选维护：请求身份、历史与中断恢复

## 症状

接入维护界面时，直接将 `crypto.randomUUID()` 用作批次/请求 ID，会因 UUID 首字符可能是数字而被 `StableId` 契约拒绝。仅在页面内存缓存重试请求，又会使刷新后的中断维护失去原请求身份。读取当前版本、历史版本与保存请求并行时，也不能让迟到响应改变另一选择的内容或加载状态。

## 根因

- UUID 的随机格式与业务稳定 ID 的字母开头约束不同。
- 一次 HTTP 失败无法证明服务端没有写入；维护版本落盘与最终回执之间存在恢复边界。
- 当前维护 head 与历史运行快照不是同一个读取范围，响应成功并不足以证明版本匹配。

## 修复

- 前端请求 ID 使用 `work-` / `skill-` 前缀；同一未改变请求的网络重试复用原 ID。
- 通过服务端未完成维护列表找回冻结请求，展示操作、原因与版本后显式恢复。页面刷新不自动执行恢复；恢复结果显示实际保存版本，不覆盖正在阅读的另一候选。
- 工作、技能及列表各自使用请求代数；切换、刷新和卸载使旧请求失效。历史读取同时核对精确 revision/version；历史表单只读，更新只依据当前 head。
- 技能修订仅从服务端确认的尚未绑定证据中选择；已 observe 的旧证据不会作为新证据发送。技能历史版本只显示该版本观察，不把当前知识投影冒充旧运行投影。

## 教训与验证

前端测试不能只模拟一个永远接受输入的 API。请求 ID、版本字段与 nullable 审核字段都要对照实际后端契约；数字开头 UUID 与错误历史版本的回归曾明确失败，再修复通过。

2026-11-07 合成隔离浏览器通过实际 HTTP 验证：工作说明 v1→v2、关系撤回与历史 v1 保留；技能新证据修订 v1→v2、争议 v3、双页面旧版本提交 409；服务端已落 v4 的中断请求刷新后显式恢复仍为 v4，随后整体撤回到 v5。该证据不代表真实语义准确率、正式数据库或模型验收。
