## Gate 0 — 启动前的安全检查（未通过不得采集）

**2026-10-20 当日勘误**：[Issue #43 最新授权](https://github.com/Serena-Lyric/TalentMind/issues/43#issuecomment-6282375204)取代初版“必须隔离库/仅落文件”前提。用户接受有上限的 M1 试采写当前原始层，并要求减少重复环境；初版留在 Git 历史与 Issue 正文供溯源。集成测试仍用隔离实例。以下是当前门禁，授权不等于已经实采成功。

1. **实际环境调查**：只读查明正在运行的采集计划任务/循环、浏览器 CDP 登录状态、`MYSQL_URL` 指向和库名、容器映射、待写表、正式库备份、工作树 Git 状态。历史 README 的 2026-08/09 运行状态不能作为当前状态。不要显示真实密码/Cookie 到日志/聊天。
2. **确认实际写入目标**：在执行的确切工作树从运行时配置只输出 host/port/database，确认是用户打算写入的现有 MySQL `jd_pool`。允许有上限真实试采直接入该原始层，不要求每次新建 DB。BOSS 列表/详情及中文平台 CLI 都会写库，没有统一已验证 `--dry-run`；`PAUSE_COLLECT` 不是 CLI 全局锁。串行运行，不与其他采集循环并发；M2 正式表、Neo4j、历史图不随之更新。
3. **准备观测**：采集 run_id、来源平台、目标页面 URL 的稳定身份/哈希、观察时间、采集入口版本 SHA、浏览器参数（不含凭据）、每条详情尝试结果、异常原因。预先定义停止条件（登录失效、验证码、封禁/限流、重复、误写库、空详情大面积出现）。**登录/验证必须由用户人工完成；不得绕过验证码或访问未公开接口。**
4. **采前原像与精确回退准备**：记录分平台 count、MAX(id)、空/重复来源身份，保存全字段可恢复快照或本批会触及的旧行原像及校验摘要。BOSS 详情 `allow_updates=True` 可 UPDATE 纯元信息且无 duties 的旧列表行，不能只备份新增行。采后按精确来源身份/ID 对账 INSERT 与 UPDATE，回退前检查并发变化，实际删除/恢复另获确认；禁止按 `id>max_id`、日期或 source 批量 DELETE。模拟/集成测试不能借此改写现库。
5. **准入证据**：实际目标（脱敏）、可用私有采前原像、无并发循环、人工登录及允许访问的站点会话、明确上限、停止/回退路径。**未通过就停在 Gate 0**；CDP 不可用时记“采集器未执行”，不记为零结果试采。

## Gate 1 — M1 三平台轻量真实试采

**当前首轮授权上限**：单个平台 **1 个关键词 × 1 个城市 × 1 页，`--max-jobs 5`、`--detail-limit 5`**，先 BOSS，验收后再逐平台推进；不使用 `--forever`。按站点允许的访问方式/节奏执行。重点先核查 BOSS **新采到的**岗位有没有详情正文，不能以旧备份 40 条列表卡判断当前采集器质量。对智联/猎聘也核实独立页面可用性和岗位/详情正确配对。

数据流：已授权可见页面 → 原始抓取候选 → 清洗 `RawJD` → 有效性判定 → 已确认的现有 MySQL `jd_pool`；私有另存列表/详情证据和行级差异。**禁止只用 `--no-details` 获取的列表卡宣称完整 JD。**

每平台出一份受控报告（分母必须标明）：
- 关键词/城市/页面、列表总数、详情尝试/成功/失败（含登录/反爬/DOM失效）、独立岗位稳定身份、源链接和观察时间、真正持久化/文件输出条数、重复/更新/跳过；
- `raw_text/duties/requirements/experience` 字段存在率、可解析正文比例、仅元信息比例、清洗后内容保持率、原始文字与选定详情页面抽样一致性；
- 5 条以内就全部人工核对，多于 5 条至少按成功/失败/异常分层核对；逐条保留原文供受控复核，公开报告只发聚合数字与脱敏样例；
- **失败与停止判定**：写入非预期库/下游表、身份源映射错误、详情错配/丢失、无法恢复完整来源、异常验证/限流：即刻停止，先修 M1 再测；详情缺失率偏高：保留失败原因，不进入 M2 质量评价的完整 JD 集。CLI `details` 是尝试数，`new` 是 INSERT 数，不能替代详情成功数或 UPDATE 数。

输出 `m1_live_trial/<batch-id>/` 下原始来源、结构化结果、字段质量/拒绝理由、运行环境标识及校验清单，全部私有保全；公开只保留引用及报告。

## Gate 2 — M2 在两组真实数据上分别验证

两个**互不混用的实验数据层**：
- **N（new）**：Gate 1 新试采、可定位详情的 JD，单独快照/哈希；不以历史正文填补缺失字段，也不与旧 JD 合并计算。
- **H（historical）**：已保存历史原始 JD，优先使用 #38/#40 固定 120 条以及根据观察质量分层选取的另一批独立记录。严格区分“2026-10-14 备份中的 2,988 行”与当前库/其他外部归档，禁止把稳定保底与候选覆盖写入同一路径。

每组分别在**真实 M2 B1→B2→B2.2 实现**（非手工拼图）运行，并对 #38 规则 v2 与 #40 规则 v3 做固定输入配对；建议以完整 M2 模块独立命令验证阶段审计后，再运行 `backend/app/graph/real_pipeline.py` 验证贯通，避免因为图投影把 M2 漏掉的记录隐去。

### 必须真实量化

| 层次 | 输入/输出及诊断 | 质量检查 |
| --- | --- | --- |
| M2 输入 | 原始行数、无正文、无详情、异常编码、可判定正文、来源缺失/身份重复 | 三平台分层统计，不能把 `needs_review` 算无效 |
| B1 | `valid / undetermined / invalid` 与 `in_scope / needs_review / out_of_scope` 分别统计；原因码、跨 v2/v3 转移、重复组 | 人工优先验 9 降级+1 升级，含混合行业软件职责与多职位整条待审 |
| B2 | 进入量、completed/partial/failed、五态和冲突、未知技能/未解析片段、原文 offset 有效性 | 重点审否定、二选一、条件、跨行共享范围；`uncertain`/mentioned 不计确定需求 |
| B2.2 | 名称候选、未解析、别名冲突及来源版本 | 无审核的候选不能写成正式技能/职业目录 |

**人工准入**：由负责人及获授权人员人工检查**两组都有覆盖**的有限证据集合（确保真正含职责、有歧义、无正文、双岗位、不同平台），先脱敏安全检查、再确定审核口径；记录人工与算法分离的标签/证据/签审时间/复核状态。没有签审时 `precision/recall=null`、不得宣称 M2 准确率；多岗位合并公告在缺少可追溯职位分段时整条 `needs_review`。是否通过 Gate 2 由实际功能、人工证据及错误风险裁定，**不得设“必须产出 N 条 required”作为准入**。

### Gate 2 通过条件

- M2 真命令与原文来源在两组真实数据上均成功执行，任一指标均能回到对应输入文件/规则版本；
- 发现的 Critical 类原文错配、误称确定要求、错误来源/偏移无法复现的问题已经纠正或对相关数据显式 fail closed；核心 B1 召回损失有人工初审与确定处理（修复/明确保留待审）；
- 初审/签审结论与评测样本选择边界清楚记录，产物逐版可重复运行，旧候选不被覆盖。
- 若以上未满足，即使技术测试全通过，也**不进入 Gate 3 正式候选接入**；可保留受限的内部演示和失败案例，但不得对外宣布真实需求分析可靠。

## Gate 3 — 新版 M2 小批量图谱功能验收

**先使用通过 Gate 2 的 N/H 各自最小真实批次**，分别通过版本化的 `real_pipeline.py run/verify` 或其审核过的后继接口生成 **facts/sources/derived/layout/manifest** 到新私有目录，并从正式 Vue 的**隔离图谱入口**读取。不得恢复旧 `rebuild_m2_graph.py` 生产重建路径。

- 显式确认：JD 节点是**原始招聘记录**、Skill 是词项/候选、`HAS_SKILL_STATEMENT` 是原文陈述而非已审需求；只有真正经过产品要求验证的边才进入下一阶段独立事实类型，不滥用 `REQUIRES`；
- 实体 ID、来源观察时间、Unicode 文本偏移、sourceIndex、原文 SHA、陈述状态、人工签审如有，都必须在 M2→M3→M5 始终一致；
- 验证同一输入两次输出字节一致、变更规则/输入版本会生成新 manifest；缺失/篡改的来源与摘要必须拒绝加载；历史图完整可切换；
- 统计事实/派生/布局各自 counts 与前后差异，不能拿纯装饰星尘代替知识节点；不为了产生相似边而从 uncertain 偷换技能要求。

**通过条件**：两组小图在真实 Vue 显示正常且逐条核验来源/关系，失败关闭和回退均通过，才考虑全量扩容。

## Gate 4 — 全量历史原始数据链路稳定性

**先盘点全量范围，再运行**。建立数据清单：来源平台、保全批次、时间/观测窗、文件/表实际行数、身份、相同 JD 重复组/跨批重叠、缺详情比率、是否演示/测试/外部归档、个人/敏感信息、可用于本次算法验收的权限及输入哈希。未获得明确许可的外部档案一律不纳入。

建议阶梯：**小批试验通过 → 100–300 → 500–1,000 → 已批准范围全部**（为工程候选规模，并非固定测试目标；每档依据样本与时间决定）。每档先跑隔离构建、验证后再进下一档；不得写入正式 MySQL/Neo4j。

稳定性必须检查：
- 分批与重试幂等（无重复创建/误覆盖）、同输入重复构建一致、失败中断与恢复、失败案例与拒绝原因留档；
- 峰值内存/运行时间/磁盘占用、来源链接回溯、数据泄露/日志敏感信息检查；
- 多平台字段缺失、跨来源相似原文、历史多岗位和冲突条件对性能与质量的影响；
- 新图加载、图节点数与真实来源数据的统计口径、前端延迟/选中路径、历史回退稳定，必要时对密度场使用已验收版本。

**停止条件**：显著新增误判、来源不一致/越权、内存不可控、崩溃不能恢复或旧图受损；保留最近已验收的小批产物，定位后重跑，**不使用全量成果倒推前阶段已通过**。

## 工程任务拆分（额度刷新时按门禁顺序执行）

- **T0（立即）**：本机/仓库只读 M1 preflight；核对运行时目标、采前原像、会话、并发与上限。复用合适的现有工作树/分支/PR，不因运维验收创建新环境。前置条件齐备后按既有授权执行单轮有界 M1，无需再次申请同一写入许可；CDP/登录阻塞则如实停止。
- **T1**：每平台少量真实 JD 的一次性采样；客观质量审查，BOSS 详情完整性优先。真实采集需要操作者人在环，站点挑战直接停止。
- **T2**：固定两组真实 JD 的 M2 运行及人工核查，补齐 B1 召回与 B2 作用域正确性；两组报告分开，旧 v2/v3 均留历史输出。
- **T3**：通过 M2 门禁后小批量 M3/Vue；最后才执行批量历史链路稳定性 T4。**T4 的范围须由负责人单独确认**。
