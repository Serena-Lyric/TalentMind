# TalentMind 仓库整理与双重角色设计

> 日期：2026-08-11  
> 状态：已获用户确认，进入实施前自审  
> 适用范围：Plan0 及后续 M1–M5 集成

## 1. 背景与目标

当前仓库同时包含已经可运行的 M1 数据采集后端、尚未迁入的 M4 原型目录，以及多份测试数据和 UI 原型。若直接删除 `backend` 或继续在根目录平行维护旧代码，会造成数据契约、导入路径和测试对象分裂。

本设计解决四个问题：

1. 明确数据采集模块和最终完整系统的唯一存放位置；
2. 在保留可复用资产的同时，停止旧代码与新方案并行演化；
3. 给出可验证、可回滚的迁移与清理顺序；
4. 为后续 Agent 和开发者提供稳定的目录边界和 README 入口。

## 2. 方案比较

### 方案 A：采集仓与集成仓分离

M1 单独维护一个仓库，A 再维护一个完整系统仓库。

- 优点：模块边界直观，单个仓库较小。
- 缺点：需要同步契约、版本和修复；最终集成容易出现“采集仓可运行、主仓不可复现”的漂移。

### 方案 B：当前仓库作为双重角色的唯一主仓（采用）

`TalentMind` 同时是 A 负责的 M1 开发仓，也是 M1–M5 集成后的完整系统仓。M1 保持在 `backend/app/collect/`，其他模块按正式目录迁入同一仓库，交接内容通过 `exchange/` 进入集成流程。

- 优点：单一代码源、单一契约、单一测试入口；Git 历史已经保存旧版本，不需要在工作树保留重复副本。
- 缺点：仓库会包含全部模块，需要清楚的目录边界和迁移门禁。

### 方案 C：在当前仓库长期保留 `legacy/` 副本

先把旧代码整体移动到 `legacy/`，新方案另建目录。

- 优点：短期心理安全感较强。
- 缺点：重复代码长期存在，导入路径、依赖和测试对象容易混淆；`legacy/` 也会被误当成可维护代码。

选择方案 B。旧版本由 Git 历史承担追溯职责，工作树只保留当前唯一实现。

## 3. 目标目录与职责

```text
TalentMind/
├─ backend/
│  ├─ app/
│  │  ├─ collect/          # M1：采集、清洗、去重、入库
│  │  ├─ job_analysis/      # M2：岗位分析
│  │  ├─ graph/             # M3：图谱节点和关系
│  │  ├─ matching/          # M4：简历解析与岗位匹配
│  │  ├─ integration/       # A：交接导入、编排、组装
│  │  ├─ routers/           # A：统一 API
│  │  ├─ contracts/         # 冻结数据契约与 DDL
│  │  ├─ db/                # 数据库连接与初始化
│  │  ├─ llm/               # LLM 适配
│  │  ├─ skills/            # 技能标准化
│  │  └─ main.py            # 后端入口
│  └─ tests/                # 后端单测与集成测试
├─ frontend/                # M5 正式前端源码
├─ exchange/                # 模块交接文件、接口自述、可审阅 Mock
│  ├─ m1/
│  ├─ m2/
│  ├─ m3/
│  ├─ m4/
│  └─ m5/
├─ data/
│  └─ local/                # 大型 CSV、网页快照、缓存；Git 忽略
├─ docs/                    # 设计、计划、决策、演示文档
├─ docker-compose.yml       # MySQL、Neo4j、Redis 等基础设施
└─ README.md                # 唯一项目入口说明
```

存放规则：

- 正式运行数据进入 MySQL、Neo4j、Redis 的 Docker 命名卷，不把数据库文件提交到 Git。
- 大型本地数据和采集缓存放 `data/local/`，只提交目录说明或小型脱敏样本。
- 模块间的小型 JSON、Mock 和接口自述放 `exchange/<模块>/`，使用 UTF-8、snake_case，并遵循 `backend/app/contracts/`。
- 正式后端源码只放 `backend/app/`；正式前端源码只放 `frontend/`。
- 不在工作树长期保留 `legacy/` 或完整重复源码副本；Git 历史负责追溯。

## 4. 迁移与清理顺序

### 阶段 0：冻结边界

建立 `exchange/`、`backend/app/integration/`、`backend/app/routers/` 的最小骨架，记录输入、输出、负责人和验证命令。此阶段不删除旧代码。

### 阶段 1：保留并验证 M1

继续使用现有 `backend/app/collect/` 和 `backend/app/contracts/ddl.sql`。先跑现有测试，再为交接输出补充最小验证。M1 只有一个正式实现位置。

### 阶段 2：逐模块迁入

按 M2 → M3 → M4 → M5 顺序迁入。每个模块必须同时完成：

- 文件进入目标正式目录；
- import、配置和测试路径切换；
- 至少一个模块级验证和一次与 A 集成的验证；
- README 或模块说明记录运行方式、输入、输出和已知限制。

### 阶段 3：清理重复内容

只有当迁移后的测试和集成验证通过，才删除原始重复目录中的源码、缓存和生成物。无法确认用途的文件先移动到明确的归档位置或保留在 Git 历史，不做盲删。

根目录 `人岗匹配/` 的处理：

- Python 源码迁入 `backend/app/matching/`；
- 测试迁入 `backend/tests/`；
- 小型测试数据迁入 `backend/tests/fixtures/matching/`；
- UI 原型迁入 `frontend/` 或 `docs/prototypes/`；
- 简历 PDF/DOCX 先脱敏，未经确认不进入正式数据目录；
- 验证通过后删除原始重复目录。

## 5. 冲突处理规则

发生旧代码与新方案冲突时，按以下优先级判断：

1. 当前数据契约 `backend/app/contracts/`；
2. 本设计和最新决策记录；
3. 通过测试的现有实现；
4. 旧目录中的未验证原型。

冲突不能靠复制两份代码解决。应选择一个正式实现，另一个只保留 Git 可追溯性；若字段或接口必须变化，先更新决策记录和契约，再同步调用方。

## 6. 完成标准

整理完成后应满足：

- 根目录有一份完整 README，能说明启动、测试、数据、交接和清理规则；
- M1 可独立运行，完整后端可通过统一入口运行；
- 每个已迁入模块只有一个正式源码位置；
- `exchange/` 中的交接文件可追溯到模块和契约版本；
- 大型本地数据不会被 Git 跟踪；
- 旧重复目录已经删除或有明确的保留理由；
- 现有测试通过，新增集成检查有明确命令。

## 7. 不在本次范围内

- 不重写现有 M1 采集管道；
- 不在没有迁移证据时删除整个 `backend`；
- 不强制统一各模块内部技术栈；
- 不把真实简历或数据库卷提交到 Git；
- 不在本次整理中创建 Git commit，除非用户另行要求。
