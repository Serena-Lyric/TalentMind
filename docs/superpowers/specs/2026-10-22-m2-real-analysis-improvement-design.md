# M2 真实岗位能力分析改进设计

## 目标

在保留冻结输入、五态、证据偏移、历史运行和正式数据边界的前提下，修复 120 条主集与 60 条留出集中可复现的高影响分析缺口，使具有明确原文依据的职责、技能要求和待审岗位大类候选得到可检查的结果，并提供最小人工复核闭环。

## 已确认约束

- M2 只读 `jd_pool`；新结果仅写 `data/local/` 中的版本化 SQLite 与报告。
- 不调用付费或外部模型，不重新采集，不写正式 MySQL/Neo4j，不发布 B3 标准岗位。
- 保持 B1、B2、B2.2、B3 既有分层和五态；无法可靠判断的内容继续保留 `uncertain`、`needs_review` 或 `unresolved`。
- 新旧版本使用相同冻结输入，旧 `run_id`、原始输入字节、旧报告和旧 SQLite 行保持不变。
- 人工审核事件只记录真实提交者提供的内容；Codex 不生成人工真值。没有人工标注时不计算真实 precision/recall。
- integration 测试默认关闭；破坏性导入必须同时具备实测目标身份和独立、限时、绑定操作的授权文件。

## 已观测问题

1. 主集 B1 的 99 条 `needs_review` 中，88 条为 `insufficient_evidence`；其中不少 `duties` 已有“系统/模块/软件”等对象和“设计/开发/测试/部署”等动作，但动作与对象的常见中文顺序未覆盖。
2. 主集 B2 的 1,224 条 `uncertain` 陈述中，884 条被标为 `unsupported_context`；规则把 JD 任意位置的“公司、项目、针对、条件、以上”等风险词扩散到全部陈述，同时不能稳定拆出同一行中的“岗位职责/任职要求”等标题。
3. 真实要求句如“熟练掌握 Python 并具备……”常因句尾附加职责或能力说明无法完整匹配，被降为 `uncertain`；岗位标题中的技能词也被当作待判断需求，增加重复噪声。
4. 主集 B3 为 0 个大类候选、1,524 条 `unsupported_duty_context`；原因不是输入全部无职责，而是分类器只接受极少数完整固定交付句。

## 处理方案

### B1

增加保守的中文职责动作/对象关系和对象前置表达，只对当前岗位职责或任职要求中的明确技术工作给出范围内的结论。标题、工具名、公司背景、否定、历史、示例和模糊条件仍不能单独确认。

### B2

将条件/风险证据限制在对应陈述及其相邻上下文；修正内联标题拆句；对明确的“熟悉/掌握/熟练使用/精通某已登记技能 + 补充说明”给出保守五态。组合条件、否定、示例、适用范围和角色主体仍按原文处理，复杂表达保留不确定。岗位标题中的技能仅作为提及，不升级为要求。

### B3

在真实职责字段中增加有限的“动作 + 技术对象/交付”大类规则，覆盖软件研发、测试质量、数据 AI、基础设施等可明确表达的职责。候选始终为 `pending_review`，`classification_complete` 与 `formal_statistics_eligible` 恒为 false，标准岗位仍然为空。

### 人工复核

在现有 SQLite 增加追加式人工审核事件，绑定 `run_id`、条目、机器结果摘要、审核决定、署名、备注和时间。现有详情页展示原文、机器证据和不确定原因；用户可提交审核、读取历史事件并导出 JSON。机器结果与人工结论分开统计。

## 验收

- 新增规则先由合成反例测试证明失败，再实现通过；保留现有否定、条件、组合、公司背景和标题冲突测试。
- 同一冻结 `main120` 与 `holdout60` 分别创建新版本运行，和旧报告逐条对照新增、减少与反转样本；所有证据位置重新校验。
- 只报告规则覆盖变化和人工签审计数；没有人工真值时不输出正式准确率。
