# TalentMind V1 恢复手册

适用：新电脑或明确新建的隔离恢复环境。依据 2026-10-14 实际恢复验证；本轮执行报告见 [仓库冻结与资产保全报告](仓库冻结与资产保全报告-2026-10-14.md)。本机备份目录不是离机副本，完整恢复前必须拿到私有备份集。

## 1. 恢复来源与数据版本

| 来源 | 能恢复 | 不能保证恢复 |
|---|---|---|
| GitHub `archive/competition-v1` | V1 正式源码、DDL、requirements、pnpm lockfile、正式文档、exchange 数据 | 原始库、配置密钥、简历、input/output、参赛完整材料、浏览器资料 |
| GitHub `master` | V1 后的保全报告和未来开发内容 | 同上；不等于冻结的 V1 |
| 完整 Git bundle | 无网络恢复 Git 历史和所有保存的 refs | Git 忽略和未跟踪文件 |
| 私有工作树包/清单 | 原版交付、采集历史、本地实验、原始 CSV、参赛材料、实际配置 | 文件内容能恢复，但旧 venv/junction 不保证跨机器直接运行 |
| SQL/Neo4j dump/冷卷/精确镜像 | 完整数据库、图谱、Redis 数据及原版本运行镜像 | 仅用 exchange 无法重建 jd_pool/signal 原始层 |

V1 源码 SHA：`4a473c2f8ee6b814acd6ed97a670563ece0f3ae0`。两种 MySQL 数据版本均已恢复验证：

- **竞赛 V1**：09-04 SQL（参赛包的 09-05 SQL 内容相同），JD 2984；分析层 717/717/275，signal 1540、skill_dict 285。
- **当前保全版本**：`mysql-current-20261014.sql`，JD 2988（多 4 条 BOSS）；其他表计数相同。原始冷卷保存这个版本。
- 两种版本图谱均以已核验的 7845 节点/11412 关系为参照。不要把原 `input` 的 719/243 回包当作 V1 演示数据。

## 2. 先核验私有备份

完整备份最初位于 `D:\backup\TalentMind-2026-10-14`，可搬到其他安全位置。备份 README、`backup-artifacts-sha256.csv`、`files-sha256-verified-private.csv`、`asset-classification-private.csv`、各验证 JSON、运行环境版本记录都应随包搬运。

对最终备份清单列出的每项重新计算 SHA-256 并逐一比对，任一不一致停止恢复。路径清单和实际配置含敏感信息，不上传公开仓库或公开报告。原 NTFS ACL 只允许当前用户/SYSTEM/管理员；复制后要为新用户重新设置权限，原 ACL 不等于加密。

冷 VHDX 包含整台 Docker 引擎的其他项目，应作为最后一级私有救援材料。**不能在当前引擎运行时覆盖、挂载写入或替换原数据盘。** 本轮只验证复制哈希，未做整盘替换启动；优先使用独立 SQL、dump、冷卷和镜像恢复。

## 3. 源码与本地资产

使用全新的 ASCII 路径，例如 `D:\TalentMindRestore`，不要覆盖旧 checkout。

在线恢复源码：

```powershell
git clone --branch archive/competition-v1 https://github.com/Serena-Lyric/TalentMind.git D:\TalentMindRestore
git -C D:\TalentMindRestore rev-parse HEAD
# 必须是 4a473c2f8ee6b814acd6ed97a670563ece0f3ae0
```

离线恢复源码（从 Git bundle，二者择一）：

```powershell
git bundle verify D:\backup\TalentMind-2026-10-14\repository-all-refs.bundle
git clone --branch archive/competition-v1 D:\backup\TalentMind-2026-10-14\repository-all-refs.bundle D:\TalentMindRestore
```

本轮文档/后续 master 的 bundle 为 `repository-final.bundle`；它不改变归档 V1 分支的 SHA。初始 `.git` 另随工作树包保留悬空对象，只作溯源，不应覆盖新 clone 的 `.git`。

在私有备份目录运行经过实际恢复验证的工具，把本地资料恢复到另一全新目录：

```powershell
python -X utf8 D:\backup\TalentMind-2026-10-14\restore-local-files.py --output D:\TalentMindLocalAssets
```

工具拒绝已有目标目录，验证路径与 SHA-256，仅恢复非生成资料；本轮实际恢复 8157 项。需要查看完整依赖副本时可加 `--include-generated`，但不会自动复刻 580 个机器相关 junction。两个 tar **必须一起携带**：首包加硬链接补包。空目录与链接信息另在元数据中；文件恢复数量并不包含这些目录条目。

核对清单后从该暂存区恢复 `input`、`output`、`data/local`、`docs/submit`、`docs/originalfile`、笔记和参赛资料到所需私有目录。遇到目标已存在时先人工比对，不能无条件覆盖。实际 `.env` 和 Claude 配置单独审阅，不把旧数据库地址/浏览器登录态直接当作新机器配置；用户 Claude 配置位于 `machine-config-private/`。

## 4. 依赖与暂停状态

实测环境为 Windows、Python **3.14.5**、Node **24.15.0**、pnpm **11.5.1**。`python-installed-20261014.txt` 记录实际 pip 版本；Git 的 requirements 与前端 lockfile 是安装入口。

```powershell
Set-Location D:\TalentMindRestore\backend
py -3.14 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
# 在本机编辑配置；密钥由私有备份/账号配置恢复，不能公开输出

Set-Location D:\TalentMindRestore\frontend
pnpm install --frozen-lockfile
pnpm run build
```

不要在已有依赖目录上接受不明的自动 purge；新目录安装后再构建。本轮已验证现有依赖下的源码测试和构建，**未验证新电脑从零下载/安装**；联网安装失败时对照实际版本记录，不能擅自批量升级依赖。若必须离线安装，现存 venv/node_modules 只能作为依赖内容与版本证据，不能承诺新路径直接可用；备份集没有专用跨机器 pip wheel/pnpm 离线安装包。

恢复并保留 `data/local/PAUSE_COLLECT`；若不恢复全部本地资料，也应创建暂停标记。不要注册采集计划任务、恢复登录或打开采集管理页来验证恢复。当前电脑未查到 `TalentMindCollect`，新机无需补建它。

## 5. 数据库：仅对全新恢复实例执行

**以下导入和图谱命令具有覆盖语义。** 先确认容器名称、项目名和卷是新建的；任何复用现有数据库的导入都要单独确认。现有系统禁止直接运行本节命令。

### 5.1 推荐：SQL + 已保存 graph.json

在没有旧 TalentMind 服务的新电脑，先核查 3306/7474/7687/6379/18000/18080 端口未占用（Windows 用 `Get-NetTCPConnection`）。用新 Compose 项目名隔离卷：

```powershell
Set-Location D:\TalentMindRestore
docker compose -p talentmind-v1-restore up -d
docker compose -p talentmind-v1-restore ps
$restoreMysql = docker compose -p talentmind-v1-restore ps -q mysql
```

选择当前 SQL 或 V1 SQL，先以二进制文件复制进**新容器**，避开 PowerShell 文本管道编码变化：

```powershell
# 当前版本示例；要竞赛 V1 就改为私有资料中 09-04/09-05 快照的准确路径
docker cp D:\backup\TalentMind-2026-10-14\mysql-current-20261014.sql "${restoreMysql}:/tmp/restore.sql"
docker exec -it $restoreMysql sh
```

仅在这个新容器 shell 内执行：

```sh
MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot --default-character-set=utf8mb4 < /tmp/restore.sql
exit
```

SQL 内含建库、选库与表覆盖语句，所以前述实例隔离不可省略。后端 `.env` 必须指向该恢复实例，密码与新 Compose 配置一致，再执行已保存图谱导入：

```powershell
Set-Location D:\TalentMindRestore\backend
.\.venv\Scripts\python.exe -m app.integration.import_graph
# 新 Neo4j 将清空再导入：预期 nodes=7845, edges=11412
```

仅有 Git 时可用显式 `import_all(r'..\exchange\m2')` 重建分析层和 graph.json 导入，但**不会恢复原始层**；它不是完整数据恢复的替代品。禁止省略参数调用 `import_all()`，也不要运行旧图谱 builder。

### 5.2 冷卷与原生 dump（离线/精确恢复）

`docker-images-v1.tar` 保存原版本镜像；`docker-volumes-private.json` 记录精确 image ID、原卷与归属。`docker load -i <镜像包>` 后核对 ID；按私有清单在新电脑重新配置所需标签，不假定 `mysql:8.0` 等滚动标签仍对应同一版本。

冷卷恢复顺序：新建卷 → 用工具容器挂载新卷及只读备份目录 → `tar -xpf` 解包相应冷卷 → 用保存的精确镜像启动新实例。MySQL、Neo4j 数据和 Redis 各使用独立新卷；Neo4j 日志另有归档。不要把冷卷 tar 解到已使用卷中；不要对运行的数据库做文件级拷贝。

原生 Neo4j dump 恢复顺序：新建空数据卷 → 在 Neo4j 未启动时，用保存的镜像运行 `neo4j-admin database load neo4j --from-path=<dump目录>` → 配置新恢复实例的认证 → 启动 → 校验图谱数量。dump 保存 `neo4j` 业务库，不包含完整 `system` 用户数据库；要保留原认证状态，使用完整冷卷。两种恢复方式本轮都实际验证过。

Neo4j 验证容器应使用专用 **internal Docker 网络**且不发布宿主端口；`--network none` 在本机镜像上会因容器 hostname 不可解析而启动退出。验证完成只停止自己的恢复容器，不删除原卷。

## 6. 验收与后续启用

SQL 恢复后查询八表记录数、JD 来源分布与 3 条 orphan 变化日志。当前版本 JD 2988、BOSS 1137；竞赛 V1 JD 2984、BOSS 1133。其他表计数与本报告一致。对当前 SQL 本轮另进行了八表扩展 checksum 比对；完整证据在私有 JSON 中。

Neo4j 查询总数、节点标签与关系类型：Job 717 / Skill 4671 / Industry 2457；REQUIRES 8866 / APPLIES_TO 2539 / RELATED_TO 7。Redis DB0 当前是 0 键，不能据此推断其他日期的缓存。

随后按 README 启动后端 **18000** 和前端 **18080**，先验 `/health`、岗位列表 total=717、图谱数量和能力日志。恢复检查不上传真实简历、不进入自动尝试采集的页面。业务浏览器验收应另安排，本轮只验证恢复数据、源码单测和前端构建。

仅在隔离数据库上开展集成测试；`test_integration_mvp` 会删除并重建岗位/技能/变化日志和图谱。不要把“测试会恢复”或“幂等”当作无覆盖风险。测试夹具清理仍须 finally/teardown 与实查零残留；保留数据基线比让工作树干净更重要。

最终在新机/外部介质再次验证哈希、数据和启动，把实际版本、恢复路径、验证结果记录下来，再决定是否移除旧机器或旧备份。
